1.工具注册表

动机：这是"可扩展"的起点。加工具 = 写一个函数 + 一行注册；不这么做，加第 5 个工具时你就开始改不动了。

解决工具schema和判断工具的if/else语句手动书写的问题
方法：建立工具注册表，实际是建立装饰器函数，将函数与工具schema绑定在一个字典里

3.结构化返回

动机：这是所有后续步骤的地基。没有结构化返回，你没法做后面要说的 trace、没法做评测、更没法把它塞进 UI 或服务。

统一返回数据的结构，为以后打基础，有助于以后做验证、测试、观察结果；同时统一结构，有助于复用

4.上下文管理

动机：能连续干活、成本有界的 Agent，才有资格谈"在生产里用"。

压缩工具返回结果长度和会话长度，防止撑爆上下文窗口
方法（截断）：限定工具返回结果长度为2000以内；会话长度为20以内，超出则删除旧的历史会话。

记住历史会话，下一轮对话可以利用历史会话记录
方法：创建会话对象，使用对象的属性来实现

5.流式输出

动机：流式解决的是"用户在工具执行和模型思考期间只能干等，体感为零"这个问题。把它做完，你的 Agent 才第一次有了"产品感"——而这正是后面接 UI、接服务的前置条件

每次agent以流式输出方式呈现内容，增加用户体验感。
方法：response API 的
stream = ...response.create(
    ...
    stream = True
)
stream 变成事件

6.追踪/观测日志

没有追踪日志，无法评判agent做的好不好，这是持续迭代的前提，必须要有观测数据
方法：创建Trace类，每一次LLM调用、tool执行都要保存下结构化trace（输入\输出\tokens使用成本\延迟）
